# PR #22B integration handoff

The foundation accepts logical data and returns text, a validated document or a preview. Connect it to the application after the collection milestone lands. [Version 1 file contract and examples](vocabulary-interchange-v1.md)

## Export

1. Capture the selected language and read a consistent snapshot of its personal entries, collections and memberships. Project PR #20’s personal fields directly. Map the final PR #21 collection identities, names, descriptions, available timestamps and member references into the documented shapes. Retain empty collections. Exclude archived entries and their memberships together.
2. Supply a single export instant to `serializeVocabulary`. Preserve the input’s IDs throughout. The writer deliberately selects portable fields even when given richer local records. Surface size or validation failures before creating a file.
3. Write the returned string to a local UTF-8 JSON file and open the platform share sheet or file destination chooser. Clean up a temporary copy after the platform finishes using it. Show the language, entry count, collection count and explicitly state that study progress and settings are excluded.

## Preview and commit

1. Let the learner choose a local JSON file. Check the reported byte size before reading when available, then decode UTF-8 and call `parseVocabulary`. Treat extensions and MIME types as picker hints. A fatal validation error or cancellation ends the flow without writes. Show the record path on errors. Show the file language and require an explicit destination choice when the active language differs.
2. Compare the validated document with a same-language snapshot, including reserved IDs for archived personal entries. Use `summarizeVocabulary` for counts, `compareEntries` for personal candidates, and the bundled registry for curated references and their display text. Show both authored sides and notes for conflicts. Report missing curated references and affected memberships. Let the learner skip those edges or cancel the import. Keep unrelated valid entries available.
3. Resolve each source ID once. For a matching identity, reuse the local ID. For a conflict or similar expression, offer **keep existing**, **keep both** or **skip**. Keeping existing explicitly references the selected local item, which can be a curated match. Keeping both allocates a fresh personal ID for the incoming content. Skipping drops the incoming entry and its edges. Preserve standalone senses by defaulting ambiguous cases to a decision. Never revive an archived row implicitly.
4. Maintain a map from each incoming vocabulary ref to its resolved destination ref (including its kind), and a separate map for incoming collection IDs. Reuse an unoccupied portable identity where the final adapter supports it. Detect reserved IDs device-wide at insertion, including collisions with another language, without exposing that language’s data. A conflicting collection name or ID needs an explicit reuse, separate-copy or skip decision. Map every membership through both maps and deduplicate the resulting pairs.
5. Commit accepted entries, collections and memberships in one SQLite transaction after confirmation. Recheck the preview’s identity, content and collection assumptions under the transaction. On stale data or failure, roll back and return to preview. Re-importing matching identities should be idempotent. A deliberately separate copy has a new identity. Preserve local revisions, schedules, exposures, ratings, sessions and enrolments. Imported vocabulary is eligible for enrolment through the existing explicit action.

Confirm PR #21’s supported external-ID insertion or remapping path, name uniqueness rules, active membership filtering and metadata timestamps before building the adapter. These are integration decisions. The JSON contract contains no SQLite table names or row keys.

## Design references and backup scope

Settings leads to a local export or import. Export shows what the file contains. Preview distinguishes ready entries, duplicates and conflicts before confirmation. The original JSON flow directly supports this milestone. Later CSV proposals require a separate product decision. [Settings](https://www.figma.com/design/vJPxcNnHyCOAp57MBh46O7/Finnish-Learning-App?node-id=455-4292) · [Export](https://www.figma.com/design/vJPxcNnHyCOAp57MBh46O7/Finnish-Learning-App?node-id=436-3826) · [Preview](https://www.figma.com/design/vJPxcNnHyCOAp57MBh46O7/Finnish-Learning-App?node-id=436-3950) · [Conflicts](https://www.figma.com/design/vJPxcNnHyCOAp57MBh46O7/Finnish-Learning-App?node-id=436-4000)

A separate full local backup would be useful for moving accumulated reviews and resuming an interrupted course of study after reinstall. The simplest candidate is a versioned local package containing a consistent SQLite snapshot from the platform’s backup facility and a validated copy of preferences. Restore would require explicit replacement confirmation, compatibility and integrity checks on a staged copy, and recovery of the prior state if replacement fails. A live SQLite file copied without its journal can omit committed data. Full backup needs its own restore and failure tests.
